## 0. 문서 운영 원칙

본 문서는 슈팅게임 기획서 v0.6의 P0 코어 시스템 4종을 프로토타입 단계에서 구현하기 위한 **엔지니어용 사양서**다. 데이터 구조, 클래스 분할, 처리 흐름을 구현 가능한 수준까지 풀어쓴다.

상위 기획 문서는 시스템 로직과 의도를 정의하며, 본 문서는 그것의 구현 매핑을 제공한다. 본 문서와 상위 문서가 충돌할 경우 상위 문서가 우선하며, 본 문서의 해당 부분을 갱신한다.

수치/데이터 항목은 다음 두 마커로 구분 표기한다.

- **[제안]** — 구현 시작점으로 사용할 값. 검증 후 조정 가능.
- **[검증]** — 본 프로토타입의 핵심 결정 대상. 플레이 결과로 확정.

검증 단계 명칭은 다음과 같이 사용한다. 이는 본 문서의 버전 번호와 무관한 개념이다.

- **본 단계 (초기 검증):** 본 문서가 정의하는 현재 프로토타입 구현 단계.
- **후속 검증 단계:** 본 단계 종료 후 진행되는 추가 검증 단계. P1 진입 전에 회복 아이템 등 일부 항목을 추가 검증한다.

### 0.1 프로토타입 예외 정책

본 문서의 Out of Scope(§1.3) 및 Stub 처리 항목(§2.2)은 프로토타입 검증을 위한 **의도적 축소**로 간주한다. 해당 항목들은 상위 문서의 최종 사양을 폐기하거나 변경하는 것이 아니라, 프로토타입 구현 범위에서만 임시 대체한다.

이 정책에 따라 다음 항목들은 "충돌"이 아닌 "의도된 임시 처리"이다.

- 슈퍼웨폰 슬롯은 정의하지만 효과는 미구현
- 기체 시스템은 스텁 1대만 사용 (특성, 다중 기체 등 미구현)
- 클리어 평가는 검증 리포트(§9.4)로 대체
- 회복 아이템은 디버그 키 또는 후속 검증 단계의 고정 위치 아이템으로 대체
- 보스는 엘리트 1체로 대체 (페이즈/파츠 미구현)
- 멈춤 트리거 시스템은 엘리트 전투 상태(§5.5.3)로 간이 대체

P1 이후 단계에서 본 문서의 임시 처리가 상위 문서의 정식 사양으로 교체된다.

## 1. 프로토타입 목표

### 1.1 검증 가설

기획서 5.2절에 따라 다음 4가지 가설을 검증한다.

| 가설 | 측정 방식 |
|------|----------|
| 지상/공중 판정 분리의 시각적 식별성 | 첫 등장 시 1초 이내에 적의 속성을 판별 가능한가 |
| 로드아웃 빌드 선택의 의미 | 다른 빌드로 같은 스테이지 플레이 시 체감 차이가 있는가 |
| 피탄 허용형 생존감 | 보호막 관리가 의식적인 자원 판단으로 작동하는가 |
| 기본 조작감 | 8방향 이동·저속 모드·사격이 슈팅게임 표준 수준인가 |

### 1.2 성공 기준

- 모든 P0 시스템이 데이터 기반으로 동작 (하드코딩된 상수 최소화). 스테이지 웨이브 포함.
- 빌드 변경 시 같은 스테이지의 플레이 양상이 명확히 달라짐
- 보호막 → 체력 → 사망 → 리스폰 → 미션 실패 흐름이 끊김 없이 동작
- 이동/사격 입력은 버퍼링 없이 다음 게임 로직 프레임에 반영된다.
- 시각 반응은 60FPS 기준 4프레임 이내에 발생해야 한다.

### 1.3 비목표 (Out of Scope)

P1 이후 단계로 미루며 본 프로토타입에서 다루지 않는다. (§0.1 예외 정책 참고)

- 기체 시스템 완전 구현 (스텁 1대만 사용)
- 슈퍼웨폰 시스템 (슬롯 데이터만 정의, 효과 미구현)
- 보스 페이즈 시스템 (엘리트로 대체)
- 미션 브리핑, 클리어 평가, 동적 캠페인, 난이도, 도전과제, 해금
- 슬롯 시너지, 드론
- 스코어링 (격파 카운터까지만)
- 회복 아이템 시스템 정식 구현 (본 단계는 디버그 키로 시뮬레이션, 후속 검증 단계에서 고정 위치 아이템으로 대체. §12 참고)
- UI 폴리싱, 사운드/이펙트 폴리싱

- 프리셋 저장/로드 → 미구현 (현재 세션 메모리만)

## 3. 기술 사양

### 3.1 엔진 및 플랫폼

- 엔진: Unreal Engine 5 (5.4 이상 권장)
- 플랫폼: PC (Windows)
- 입력: 키보드 + 게임패드 (XInput, Enhanced Input 사용)

### 3.2 좌표계 및 단위

- UE 표준 cm 좌표계
- 플레이 영역: **[제안]** 가로 1600cm × 세로 1200cm (직교 카메라 기준)
- 진행 방향 축: **[검증]** 카메라 세팅 후 결정 (X-forward 또는 Y-up)
- 모든 속도 단위는 cm/s
- 화면 좌표 규약: §4.8 ESpawnAnchor 참고

### 3.3 데이터 테이블

스텁 컨텐츠는 UE DataTable로 관리한다. 행 구조체는 §4의 정의를 따른다.

- CSV 임포트 우선 (즉석 수정성)

## 4. 데이터 구조

이하 시그니처는 C++ 풍 의사코드. 실제 구현 시 UPROPERTY/UCLASS 매크로 등은 엔진 컨벤션에 따라 부착.

### 4.1 속성 enum

```cpp
enum class EAttribute : uint8
{
    None    = 0,   // 플레이어 기체 전용
    Ground  = 1,
    Air     = 2,
};

// 무장/탄환은 속성 배열 (단일/복수 가능)
TArray<EAttribute> AttributeArray;

// 적은 단일 속성 또는 양면 (Ground+Air 둘 다 보유)
struct FEnemyAttribute { bool bGround; bool bAir; };
```

**속성 일치 판정** (정적 유틸):

```cpp
static bool IsMatch(const TArray<EAttribute>& BulletAttrs, const FEnemyAttribute& EnemyAttr)
{
    for (auto a : BulletAttrs)
    {
        if (a == EAttribute::Ground && EnemyAttr.bGround) return true;
        if (a == EAttribute::Air    && EnemyAttr.bAir)    return true;
    }
    return false;
}
```

### 4.2 무장 데이터 (FWeaponRow)

기본 무기와 특수 무장은 동일한 행 구조체를 공유. 슬롯 분류는 Category 필드로 표기.

| 필드 | 타입 | 설명 |
|------|------|------|
| WeaponID | FName | 고유 식별자 (PK) |
| DisplayName | FText | UI 표시 이름 |
| Category | EWeaponCategory | Primary / Special |
| AttributeArray | TArray<EAttribute> | 속성 배열 |
| BaseDamage | int32 | 탄환 1발 데미지 (최소 1) |
| FireRate | float | 초당 발사 수. **0보다 커야 한다 (§5.2.7 참고)** |
| FireMode | EFireMode | Auto / SingleShot (§5.2.7 참고) |
| ProjectileSpeed | float | 탄속 (cm/s) |
| HitBehavior | EHitBehavior | Destroy / Penetrate / LimitedPenetrate |
| PenetrationLimit | int32 | LimitedPenetrate 시 N (그 외 무시) |
| MuzzleOffset | FVector | 발사 위치 오프셋 (기체 기준) |
| ProjectileMesh | TSoftObjectPtr<UStaticMesh> | 탄환 비주얼 |
| ProjectileColor | FLinearColor | 속성 색상 (시각 식별 검증용) |

```cpp
enum class EHitBehavior : uint8 { Destroy, Penetrate, LimitedPenetrate };
enum class EWeaponCategory : uint8 { Primary, Special };
enum class EFireMode : uint8 { Auto, SingleShot };
```

> 프로토타입에서는 모든 무장이 `Auto`. `SingleShot`은 확장 여지로만 정의.

### 4.8 ESpawnAnchor 와 화면 좌표

```cpp
enum class ESpawnAnchor : uint8
{
    TopLeft,
    TopCenter,
    TopRight,
    Left,
    Center,
    Right,
    BottomLeft,    // 사용 빈도 낮음. 정의만 유지.
    BottomCenter,
    BottomRight,
};
```

**중요: 본 앵커 좌표는 화면 경계점이 아니라, 화면 안쪽 여백을 둔 프로토타입용 진입 기준점이다.** 플레이 영역이 1600×1200(중심 (0,0), 경계 X ±800 / Y ±600)일 때 앵커는 X ±700 / Y ±500에 위치한다. 적이 화면 경계에서 갑자기 등장하기보다 안쪽 여유 지점에서 등장하도록 의도된 값이다. 정밀 위치가 필요하면 `SpawnOffset`으로 조정한다.

| 앵커 | (X, Y) 좌표 | 비고 |
|------|------------|------|
| TopLeft | (-700, 500) | 화면 상단 좌측 진입 (경계 아님, 안쪽 여백) |
| TopCenter | (0, 500) | 화면 상단 중앙 |
| TopRight | (700, 500) | 화면 상단 우측 진입 |
| Left | (-700, 0) | 좌측 중단 |
| Center | (0, 0) | 화면 중앙 (엘리트 등장 등) |
| Right | (700, 0) | 우측 중단 |
| BottomLeft | (-700, -500) | (보조) |
| BottomCenter | (0, -500) | (보조) |
| BottomRight | (700, -500) | (보조) |

`AnchorToWorld()` 헬퍼는 위 매핑을 그대로 구현. 플레이 영역 크기가 변경되면 매핑도 함께 갱신.

> 화면 진행 축이 §3.2에서 결정되면 위 좌표의 Y 성분이 적절한 축으로 매핑된다. 본 표는 카메라 평면 기준의 논리 좌표.

## 5. 시스템별 구현 사양

### 5.1 지상/공중 판정 분리

#### 5.1.1 책임 범위

- 탄환↔적 충돌 시 속성 비교
- 일치: 데미지 적용 + 히트 이펙트 + HitBehavior 처리
- 불일치: 데미지 무시 + 히트 이펙트 미재생 + 탄환 그대로 진행
- 적→플레이어 방향에는 속성 시스템 미적용 (단방향)

#### 5.1.2 처리 시퀀스

```
[Projectile.OnHit(Enemy)]
  │
  ├── IsMatch(BulletAttrs, EnemyAttr) ?
  │
  ├── YES → Enemy.ApplyDamage(BaseDamage)
  │         PlayHitEffect()
  │         HandleHitBehavior():
  │           Destroy            → DestroyActor
  │           Penetrate          → 그대로
  │           LimitedPenetrate   → ++count, count >= N → DestroyActor
  │
  └── NO  → 데미지 무시
            히트 이펙트 미재생
            탄환 그대로 진행 (콜리전 응답을 ignore-overlap으로 처리)
```

> 프로토타입에서 보스 파츠 단위 콜리전은 다루지 않음. 엘리트도 단일 콜리전 + 양면 속성으로 처리.

#### 5.1.3 클래스 분할

```
AProjectileBase : AActor
  - TArray<EAttribute> AttributeArray
  - EHitBehavior HitBehavior
  - int32 PenetrationLimit
  - int32 PenetrationCount
  - OnComponentHit() / OnComponentBeginOverlap()

UAttributeComponent : UActorComponent
  - FEnemyAttribute Attribute   // 적/엘리트에 부착
  - 플레이어에는 부착하지 않거나 None 상태로 유지

UAttributeMatcher (정적 유틸)
  - IsMatch(BulletAttrs, EnemyAttr) → bool
```

#### 5.1.4 시각 식별성 — 핵심 검증 항목

기획서 7장의 "시각적 식별 레이어 세부 적용"이 본 프로토타입의 핵심 결정 사항. 다음 후보를 모두 구현하고 토글 가능하게 하여 비교한다.

| 후보 | 구현 |
|------|------|
| 색상 단독 | 지상=주황 계열, 공중=시안 계열 |

**[검증]** — 새 플레이어가 가장 빠르고 정확하게 식별하는 조합 결정.

#### 5.2.7 발사 규칙

WeaponSystemComponent는 다음 규칙으로 무장을 발사한다.

**기본 원칙:**

| 항목 | 규칙 |
|------|------|
| FirePrimary | 버튼 홀드 시 자동 연사. Primary 무장 1종 발사. |
| FireSpecial | 버튼 홀드 시 **장착된 특수무장 2개가 각각 자동 발사**. |
| 쿨타임 | 각 무장이 자기 FireRate에 따른 **개별 발사 쿨타임**을 가짐. |
| 동시성 | Primary와 Special은 동시에 발사 가능. |
| Special1 / Special2 | 쿨타임을 공유하지 않음. 각자 발사 가능 상태일 때 발사. |

**FireRate 유효성:** FireRate는 0보다 커야 한다. 0 이하 값은 데이터 오류로 간주하고 해당 무장은 발사하지 않으며, 로드 시 워닝 로그를 남긴다. 런타임 분기에서도 방어 가드를 둔다.

**처리 흐름:**

```cpp
void UWeaponSystemComponent::Tick(float DeltaTime)
{
    // Primary
    PrimaryCooldown -= DeltaTime;
    if (bFirePrimaryHeld && PrimaryCooldown <= 0
        && PrimaryRow != nullptr && PrimaryRow->FireRate > 0.0f)
    {
        FireProjectile(PrimaryRow);
        PrimaryCooldown = 1.0f / PrimaryRow->FireRate;
    }

    // Special 1
    Special1Cooldown -= DeltaTime;
    if (bFireSpecialHeld && Special1Cooldown <= 0
        && Special1Row != nullptr && Special1Row->FireRate > 0.0f)
    {
        FireProjectile(Special1Row);
        Special1Cooldown = 1.0f / Special1Row->FireRate;
    }

    // Special 2 — Special 1과 독립
    Special2Cooldown -= DeltaTime;
    if (bFireSpecialHeld && Special2Cooldown <= 0
        && Special2Row != nullptr && Special2Row->FireRate > 0.0f)
    {
        FireProjectile(Special2Row);
        Special2Cooldown = 1.0f / Special2Row->FireRate;
    }
}
```

**의도:**
- 로드아웃 2슬롯의 의미를 살리되 입력 복잡도를 늘리지 않는다.
- 같은 무장을 양 슬롯에 넣으면 사실상 화력 2배 효과 (FireRate 2배). 이는 의도된 빌드 선택.
- 다른 무장을 넣으면 두 무장의 발사 패턴이 자연스럽게 겹친다.

### 5.3 생존

#### 5.3.1 책임 컴포넌트

```
USurvivalComponent : UActorComponent
  - int32 MaxHealth, CurrentHealth
  - int32 MaxShield, CurrentShield
  - float ShieldRegenInterval
  - float ShieldRegenAccumulator
  - bool bIsInvincible
  - float InvincibilityRemaining
  - int32 Lives                    // 잔기

  - ApplyDamage(int32 Damage)
  - Heal(int32 Amount)             // 체력 우선
  - Tick(DeltaTime)                // 무적 카운트다운, 보호막 재생
  - OnDeath()
  - Respawn()                      // 잔기 -1, 풀충전, 3초 무적
```

#### 5.3.2 자원 초기화

- MaxHealth ← FShipRow.MaxHealth (스텁: 5)
- MaxShield ← FShieldRow.MaxShield (스텁 보호막에 따라 2 또는 4)
- ShieldRegenInterval ← FShieldRow.RegenInterval
- Lives ← 1 (예비기 1기, 매 미션 시작 시 초기화)

#### 5.3.3 피격 처리 시퀀스 (핵심)

```cpp
void USurvivalComponent::ApplyDamage(int32 Damage)
{
    if (bIsInvincible) return;                  // 무적 중 무시

    const int32 FinalDamage = FMath::Max(Damage, 1);   // 최소 1

    if (CurrentShield >= 1)
    {
        // 보호막은 데미지만큼 감소.
        // 단, 데미지가 현재 보호막보다 커도 초과분은 체력으로 전달하지 않는다.
        const int32 ShieldDamage = FMath::Min(CurrentShield, FinalDamage);
        CurrentShield -= ShieldDamage;

        if (CurrentShield == 0)
        {
            OnShieldBreak();
        }

        return;   // 체력 데미지 없음, 피격 후 무적 발동 없음
    }

    // 보호막 0 상태에서 피격
    CurrentHealth -= FinalDamage;
    StartInvincibility(HitInvincibilityDuration);    // 피격 후 무적 발동

    if (CurrentHealth <= 0)
    {
        OnDeath();
    }
}
```

**핵심 규칙 두 가지:**

1. **보호막은 데미지만큼 감소한다.** 1 데미지면 1만큼, 3 데미지면 3만큼 감소. MaxShield 차이가 의미를 갖는다.
2. **데미지가 잔량보다 커도 초과분은 체력으로 전달하지 않는다.** 보호막은 "최후의 방패"로 기능한다.

이 두 규칙의 조합으로 보호막의 두 차원(총량, 재생 속도)이 빌드 선택의 의미를 갖는다.

#### 5.3.4 보호막 파괴 처리

```cpp
void USurvivalComponent::OnShieldBreak()
{
    if (BreakInvincibilitySec > 0.0f)
    {
        StartInvincibility(BreakInvincibilitySec);   // 보호막 파괴 무적
    }
    // 그 외 특수 효과(주변 데미지, 슈퍼웨폰 충전 등)는 P1 이후
}
```

#### 5.3.5 보호막 자동 재생

```cpp
void USurvivalComponent::Tick(float DeltaTime)
{
    // 무적 카운트다운
    if (bIsInvincible)
    {
        InvincibilityRemaining -= DeltaTime;
        if (InvincibilityRemaining <= 0.0f) bIsInvincible = false;
    }

    // 보호막 재생
    if (CurrentShield < MaxShield)
    {
        ShieldRegenAccumulator += DeltaTime;
        if (ShieldRegenAccumulator >= ShieldRegenInterval)
        {
            CurrentShield += 1;
            ShieldRegenAccumulator -= ShieldRegenInterval;
        }
    }
}
```

#### 5.3.6 무적 상태머신

상태:
- `Vulnerable` (피격 가능)
- `Invincible_Hit` (피격 후 무적, 2~3초 **[검증]**)
- `Invincible_ShieldBreak` (보호막 파괴 무적, 보호막 데이터로 결정)
- `Invincible_Respawn` (리스폰 무적, 3초)

세 종류 모두 단일 `bIsInvincible + InvincibilityRemaining` 변수로 표현. **새 무적 발동 시 기존 잔여 시간과 신규 지속 시간 중 더 긴 값을 적용한다.** 짧은 무적이 더 긴 무적을 덮어쓰는 버그를 방지한다.

```cpp
void USurvivalComponent::StartInvincibility(float Duration)
{
    bIsInvincible = true;
    InvincibilityRemaining = FMath::Max(InvincibilityRemaining, Duration);
}
```

**무적 동안 공격/이동/회복 모두 가능**, 피격만 무시.

#### 5.3.7 잔기/리스폰

```cpp
void USurvivalComponent::OnDeath()
{
    if (Lives > 0)
    {
        Lives -= 1;
        Respawn();
    }
    else
    {
        GameMode->OnMissionFail();
    }
}

void USurvivalComponent::Respawn()
{
    CurrentHealth = MaxHealth;
    CurrentShield = MaxShield;
    ShieldRegenAccumulator = 0.0f;
    StartInvincibility(3.0f);
    PlayerPawn->SetActorLocation(SpawnLocation);
}
```

#### 5.3.8 회복 (프로토타입 단순화)

- 본 단계에서 회복 아이템 시스템은 미구현
- 디버그 키 F5(체력 풀충전), F6(보호막 풀충전)으로 시뮬레이션
- 보호막 자동 재생만 정상 구현
- 후속 검증 단계에서 고정 위치 회복 아이템 추가 예정 (§12)

#### 5.3.9 저체력 경고

- 화면 주변 이펙트 (Post Process 또는 UMG 오버레이)
- **[제안]** 임계값: CurrentHealth ≤ 1 (MaxHealth 5 기준)

bool ULoadoutManager::TryLaunch()

### 5.5 스테이지 컨트롤러

P0 시스템의 보조 구현. 정식 스테이지 구조 시스템(시스템_스테이지구조_v0.2)의 완전 구현이 아닌, P0 검증을 위한 간이 버전이다.

#### 5.5.1 책임

- 자동 스크롤 (DataTable에서 속도 로드)
- 시간 기반 웨이브 트리거 (FPrototypeWaveRow 순회)
- 엘리트 등장 시각에 도달하면 엘리트 전투 상태로 전환
- 엘리트 격파 또는 제한 시간 초과 시 미션 종료

#### 5.5.2 클래스 구조

```
AStageController : AActor
  - FPrototypeStageRow StageRow
  - TArray<FPrototypeWaveRow> Waves  // StageID 필터링 후 캐시
  - float ElapsedTime
  - int32 NextWaveIndex
  - EStageState State                 // Timeline / EliteCombat / Ended

  - void StartStage(FName StageID)
  - void Tick(float DeltaTime)
  - void OnEliteDefeated()
  - void OnEliteTimeout()
```

#### 5.5.3 엘리트 전투 상태

엘리트 등장 시각에 도달하면 다음 처리가 자동 진행된다. 이는 정식 멈춤 트리거 시스템(시스템_스테이지구조_v0.2 §5)의 간이 대체이다.

| 항목 | 처리 |
|------|------|
| 자동 스크롤 | 정지 |
| 후속 웨이브 스폰 | **중단** (WaveTable의 잔여 행은 무시) |
| 화면 위 기존 잡몹 | **유지**. 기존 이동 패턴 그대로 진행하다 화면 밖으로 나가면 제거. |
| 엘리트 스폰 | EliteEnemyID로 1체 스폰 (앵커 Center) |
| 제한 시간 카운트다운 | EliteTimeLimit 적용 시작 |

> 60~80초 구간에서 보호막 압박을 받은 상태가 엘리트 전투로 자연스럽게 이어지도록, 잡몹은 강제 제거하지 않는다. 단, 신규 잡몹은 더 이상 스폰되지 않으므로 시간이 지나면 잡몹이 자연 소거되어 엘리트 단일 전투로 수렴한다.

상태 전환:

```
[Timeline] ──(t >= EliteTriggerTime)──→ [EliteCombat]
                                            │
                            ┌───────────────┴───────────────┐
                  엘리트 격파                       제한 시간 초과
                            │                               │
                            ▼                               ▼
                  [Ended: Cleared]              [Ended: Failed]
```

#### 5.5.4 미션 종료 처리

- **클리어**: 엘리트 격파 시점에 GameMode.OnMissionClear() 호출
- **실패**: 엘리트 제한 시간 초과 또는 잔기 0 사망 시 GameMode.OnMissionFail() 호출
- 두 경우 모두 §9.4 검증 리포트 출력

> 시간 경과만으로 미션 클리어되는 경로는 없다. 엘리트 격파가 유일한 클리어 조건. 이는 빌드별 화력 차이를 측정하기 위한 의도적 설계.

#### 7.5.1 적 공격 패턴 동작 명세

본 프로토타입은 적 공격 패턴 시스템의 완전 구현이 아니므로, 다음 3개 패턴을 EnemyAIComponent 내부 코드 분기로 처리한다. 정식 패턴 시스템(별도 DataTable, 패턴 그래프 등)은 P1 이후.

**Single**
- 매 `FireInterval` 마다 1발 발사
- 발사 방향: 발사 시점의 **플레이어 현재 위치 방향**
- 적탄 1개 사용, 속도는 `EnemyProjectileSpeed`

**Spread3**
- 매 `FireInterval` 마다 3발 동시 발사
- 중심 방향: 발사 시점의 플레이어 현재 위치 방향
- 발사 각도: 중심 기준 **-15° / 0° / +15°**
- 적탄 3개 사용, 모두 동일 속도

**Rotate3**
- 매 `FireInterval` 마다 3발 동시 발사
- 발사 각도: 내부 기준 각도 θ를 기준으로 **θ / θ+120° / θ+240°** 방향
- 발사 후 기준 각도를 **+30°** 회전 (다음 사이클을 위해 누적 회전)
- 플레이어 위치를 향해 조준하지 않음. 회전 패턴 자체가 위협.

세 패턴 모두 적이 살아있는 동안 계속 반복.

**화면 밖 처리:** 적이 화면 밖 판정 영역을 벗어나면 **즉시 제거되며, 발사도 중단된다.** 유지 시간이나 페이드 처리는 본 단계에서 도입하지 않는다. 정밀 보존 정책은 P1 이후 별도 검토.

| F3 | 적 속성 라벨 강제 표시 (시각 식별 검증용) |
| F5 | HP 풀회복 |
| F6 | Shield 풀충전 |
| F7 | 무적 토글 |
| F8 | 스테이지 재시작 |
| F9 | 자동 스크롤 일시정지 |
| F10 | 시각 식별 디자인 안 순환 (5.1.4) |
| 1~3 | 로드아웃 빌드 프리셋 핫스왑 |

### 9.3 로깅

각 이벤트 시 CSV 로그 출력 (검증 후 분석용):

- 격파: timestamp, EnemyID, EnemyAttr (Ground/Air/Mixed), WeaponID, AttrMatch, Damage
- 피격: timestamp, IncomingDamage, ShieldBefore, ShieldAbsorbed, HealthBefore, HealthAfter, Invinc
- 출격: timestamp, FullLoadout snapshot
- 미션 종료: timestamp, Result, ElapsedSec, EliteDefeated, KillsByAttr

### 9.4 미션 결과 검증 리포트

미션 종료 시(클리어 또는 실패) 화면에 다음 정보를 표시한다. 이는 정식 클리어 평가 시스템(시스템_클리어평가_v0.2)이 아닌, 빌드 검증용 리포트이다.

**Mixed 적 격파율 집계 정책:** 양면 속성 적은 **Air 카운트와 Ground 카운트 양쪽에 동시 포함**한다. 이는 상위 클리어 평가 시스템(시스템_클리어평가_v0.2 §2.3)의 카운트 규칙과 정합되도록 한 것. 추가로 **보조 항목으로 Mixed 별도 카운트도 함께 표시**하여, 빌드 검증 시 양면 적 대응력을 별도로 확인할 수 있게 한다.

```
=========================
  Mission Result
=========================
  Result            : Cleared / Failed
  Clear Time        : 92.4s

  [Loadout]
   Ship             : Proto_Ship_01
   Primary          : Proto_PW_AA
   Special 1        : Proto_SW_AA1
   Special 2        : Proto_SW_AG1
   Shield           : Proto_Shield_Fast

  [Kills]   (Mixed enemies counted on both Air and Ground)
   Air     enemies  : 17 / 20   (85.0%)
   Ground  enemies  :  8 / 14   (57.1%)

  [Auxiliary]
   Mixed only       : 3 / 4     (75.0%)
   Elite defeated   : Yes

  [Damage Taken]
   Total hits       : 7
   Shield absorbed  : 5
   Health damage    : 2

  [Deaths]
   Death count      : 0
=========================
```

위 예시에서:
- Air enemies 분모 20 = 순수 공중 적 16 + Mixed 적 4
- Ground enemies 분모 14 = 순수 지상 적 10 + Mixed 적 4
- Mixed 적은 양쪽 분모/분자에 카운트되며, Auxiliary 섹션에 단독 카운트가 별도 표시

엔진 콘솔 로그에 동일 정보 출력. CSV 행으로 누적 기록.

## 10. 구현 순서 권장

### Phase 1 — 토대 (1~2주)
1. PlayerPawn + Enhanced Input + 8방향 이동 (속성 없음)
2. 화면 경계 클램프, 자동 스크롤 (StageController 기본형)
3. 단일 무장 발사 (속성 없음)
4. 단일 적 스폰 (HP만, 속성 없음)

### Phase 2 — 핵심 시스템 (2~3주)
5. EAttribute / AttributeComponent / AttributeMatcher
6. 판정 분리 적용 (탄환↔적 콜리전 시퀀스)
7. SurvivalComponent (HP/Shield/무적/잔기) — 보호막 흡수 규칙 + 무적 max 정책 정확히 구현
8. 시각 식별 디자인 4안 토글 구현
9. WeaponSystemComponent (Primary + Special1 + Special2 독립 쿨타임, FireRate 가드)

### Phase 3 — 로드아웃 (1주)
10. DataTable 도입 (무장/보호막/기체)
11. EquipmentRegistry / LoadoutManager
12. GameMode.StartMission 빌드 주입
13. 디버그 로드아웃 UI

### Phase 4 — 스테이지·검증 (1~2주)
14. ESpawnAnchor 매핑 + StageController + WaveSpawner (FPrototypeStageRow / FPrototypeWaveRow 기반)
15. 스텁 적 4종 + AI 패턴 (Single / Spread3 / Rotate3 코드 분기)
16. 엘리트 전투 상태 (스크롤 정지, 잡몹 유지·신규 스폰 중단, 제한 시간, 클리어/실패 분기)
17. 디버그 HUD, 치트키, 로깅, 검증 리포트

**총 추정: 5~8주 (1인 풀타임 기준)**.

본 4 Phase 종료 후 §12.1의 후속 검증 단계 진행.
