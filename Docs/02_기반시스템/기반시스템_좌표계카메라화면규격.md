## 1. 개요

본 문서는 모든 게임플레이 구현의 전제가 되는 좌표계, 카메라, 화면 규격을 정의한다. 이 문서의 결정들은 스폰 좌표, 이동/스크롤 수치, 스테이지 데이터, UI 배치의 공통 기준이 되며, 구현이 진행된 후에는 변경 비용이 매우 크므로 프로토타입 착수 전에 확정한다.

일부 항목은 프로토타입에서 최종 검증 후 확정하며, 해당 항목은 [검증]으로 표기한다.

## 2. 진행 축 — 확정

**게임 진행 축은 화면 세로 축으로 확정한다.**

- 방향의 정의 (혼동 방지를 위해 4가지를 분리한다):

| 개념 | 방향 |
|------|------|
| 논리적 스테이지 진행 방향 | 화면 위쪽 |
| 플레이어 기본 전방·기본 발사 방향 | 화면 위쪽 |
| 적의 기본 등장 방향 | 플레이필드 상단에서 등장 |
| 배경의 화면상 기본 이동 방향 | 화면 아래쪽 — 카메라/스테이지가 논리 진행 방향으로 전진한 결과 |
- 엔진 내 좌표 축 매핑(어느 월드 축을 화면 세로에 대응시킬지)은 엔진 표준 관례에 맞춰 프로그래머가 확정하되, 한 번 정한 매핑은 전 시스템에서 일관 유지한다
- 모든 스폰 위치, 이동 패턴, 발사 방향 정의는 "화면 기준 상/하/좌/우" 개념으로 기술하며, 엔진 축으로의 변환은 구현 계층에서 일괄 처리한다

## 3. 카메라와 투영

### 3.1 투영 방식 — 직교 투영 채택

**직교(Orthographic) 투영을 채택한다.**

채택 근거:
- 근수직 탑뷰에서 원근 왜곡이 없어 유닛 크기와 위치의 가독성이 일정함
- 화면 위치에 따른 히트박스 체감 차이가 없음 (슈팅 게임의 판정 신뢰성)
- 스테이지 어디서든 유닛의 보이는 형태가 동일하여 시각 식별 규칙이 안정적

직교 투영의 약점인 깊이감 손실은 라이팅으로 보상한다 (3.2절).

**프로토타입 기본 구현은 직교 투영이다.** [검증] 약한 원근(FOV 좁은 원근 투영)과의 비교를 1회 수행하되, 비교 결과가 특별히 우수할 때만 변경을 검토한다 — 임시 후보가 아니라 "직교 유지 여부 확인" 절차다.

### 3.2 라이팅 기반 깊이 표현

직교 투영에서의 깊이감은 **다이나믹 라이트의 각도 오프셋**으로 만든다.

- 방향광(디렉셔널 라이트)을 카메라 축과 다른 각도로 기울여 배치한다
- 오브젝트의 그림자가 본체와 어긋난 위치에 생성되어 깊이감이 발생한다
- **공중 유닛은 고도만큼 그림자가 본체에서 멀리 분리**되고, **지상 유닛은 그림자가 본체에 밀착**된다 — 이 그림자 분리 거리가 지상/공중 시각 식별의 1차 신호가 된다 (지상공중판정분리 시스템과 직결)

운영 원칙:
- 라이트 각도는 전 스테이지 공통 기준값을 두되, 스테이지 분위기 연출을 위한 미세 조정은 허용 (단, 그림자 분리 방향이 뒤집히는 수준의 변경은 금지 — 식별 규칙 훼손)
- 그림자는 다이나믹 섀도를 기본으로 하되, 유닛 수 증가로 성능 문제가 발생하면 잡몹에 한해 데칼 그림자로 폴백 가능하도록 구현 여지를 남긴다. 폴백 시에도 "공중 = 그림자 분리, 지상 = 그림자 밀착" 규칙은 동일하게 유지한다

[검증] 그림자 분리만으로 게임 속도에서 지상/공중이 즉각 구분되는지 — 프로토타입 시각 식별 검증 항목과 동일. 아트 버티컬 슬라이스에서 함께 확인한다.

### 3.3 카메라 각도

- 완전 수직이 아닌 **근수직(약간 기울인) 각도**를 기본으로 한다 — 유닛의 측면 실루엣이 살짝 보여 입체감과 기종 식별에 유리
- 구체 각도 값은 [검증] — 프로토타입에서 후보 2~3개 각도를 토글 비교하여 확정
- 카메라 각도와 라이트 각도는 세트로 검증한다 (각도 조합에 따라 그림자 분리감이 달라짐)

### 3.4 게임플레이 판정 평면과 렌더 고도의 분리

지상/공중은 **논리 속성**이고, 시각 고도는 **표현**이다. 두 층을 명확히 분리한다.

**게임플레이 판정 평면 (단일 공통 평면):**
- 이동, 타겟팅, 탄환 충돌, 범위 판정, 램 overlap 판정은 전부 **하나의 공통 평면 위에서** 수행한다
- 지상/공중 속성은 이 평면 위의 논리 속성이며, 속성 일치 여부가 데미지 유효성을 결정한다 (판정 분리 시스템)
- 공중 유닛의 히트박스는 시각 고도만큼 올라가지 않는다 — 모든 히트박스·판정 위치는 판정 평면에 있다
- 거리 계산(유도 표적 거리, 범위 반경, 램 거리)은 전부 판정 평면 위의 2D 거리다

**렌더 고도 (시각 전용):**
- 외형 메시와 그림자의 시각 표현용 고도 — 공중 유닛의 메시를 고도만큼 올려 그림자 분리를 만든다 (3.2)
- 렌더 고도는 히트박스·판정 위치·이동 범위·사거리·범위 반경 계산에 **일절 사용하지 않는다**
- 기체·유닛 프리팹 구조는 플레이어 기동 시스템의 공통 앵커 구조와 동일하다: 판정 기준점(판정 평면 위) / 히트박스 앵커 / 발사구 앵커 / 외형부(렌더 고도·기울기·애니메이션 적용)

**투영 어긋남 보정 [전달 사항]:** 근수직 카메라에서 메시를 렌더 고도만큼 올리면 화면 투영 위치가 판정 앵커와 어긋난다. 외형 위치와 판정 위치의 시각적 괴리가 과도하지 않도록 보정 방식(외형 오프셋 상쇄 등)을 프로그래머와 확정한다 [검증 — 카메라 각도 검증과 세트].

## 4. 화면 규격

### 4.1 플레이필드와 좌우 영역

세로 진행 게임을 가로 모니터(16:9)에서 운영하므로, 화면은 **중앙 플레이필드 + 좌우 영역**으로 분할된다.

- 플레이필드 비율: [검증] 후보 3:4 / 9:16 / 중간값. 프로토타입에서 적탄 밀도·기동 공간 체감으로 확정
- 플레이필드는 화면 중앙 고정

### 4.2 좌우 영역 정책 — 월드 연속 + 연출 예약 공간

**좌우 영역은 검은 레터박스로 처리하지 않는다. 플레이필드와 이어지는 월드 배경이 계속 보이며, 필드와 동일하게 스크롤된다.**

- 좌우 영역은 배경 월드의 연속이다. 예: 협곡 통과 미션이라면 필드는 협곡 바닥, 좌우 영역은 협곡 양쪽의 절벽 상단이 보인다. 해상 미션이라면 먼 바다가 이어진다
- 스크롤은 플레이필드와 동기화되어 "플레이어 옆을 지나가는" 공간감을 만든다
- 이 정책의 의도: "화면 밖은 죽은 공간"이 아니라 "게임 세계가 화면 밖으로 이어져 있다"는 인상. 스테이지 테마별로 좌우 영역이 지형적 의미를 가진다

**필드 ↔ 좌우 영역의 시각적 경계 처리는 필수다.** 판정이 발생하는 공간과 아닌 공간이 즉각 구분되어야 한다.

**경계 처리 원칙 — 테마별 환경 요소로 표현한다.** 인공 경계선이 아니라, 각 스테이지 테마가 자기 세계의 논리로 경계를 만든다.

| 테마 예시 | 경계 장치 |
|-----------|-----------|
| 협곡 | 필드=협곡 바닥, 좌우=절벽 상단. 절벽이 필드 쪽에 드리우는 그림자 밴드가 자연 경계 (라이트 각도 시스템과 일치) |
| 해상 | 좌우 영역에 구름 프랍을 더 높은 밀도로 배치하여 경계 형성 |
| 성층권 초고공 | 외곽으로 갈수록 어두워지는 처리 — 성층권과 우주의 경계면을 표현 |

- 공통 베이스로 좌우 영역의 명도·채도를 필드보다 낮게 유지한다 (어느 테마든 판정 영역 인지가 성립하는 최소 보장). 그 위에 테마별 경계 장치가 얹힌다
- **경계 그림자 밴드의 색상은 레벨의 환경 팔레트에 맞춰 조정한다** (협곡=암갈색 그림자, 해상=한색 계열 등). 인공적인 단일 색 밴드를 전 스테이지에 일괄 적용하지 않는다
- **좌우 영역의 환경 프랍은 연출 자원을 겸한다.** 예: 해상 테마의 구름 프랍은 기체형 슈퍼웨폰(대출력 레이저)의 압력으로 밀려나는 연출 재료가 된다. 테마 설계 시 경계 장치와 연출 활용을 함께 계획한다
- [검증] 명도·채도 차이 + 테마 장치만으로 게임 속도에서 경계 인지가 충분한지 프로토타입에서 확인. 부족할 경우에 한해 인공 경계선을 최후 수단으로 검토

**연출 활용:** 좌우 영역과 플레이필드 사이의 연출은 **양방향**으로 발생할 수 있다

| 방향 | 의미 | 예시 |
|------|------|------|
| 진입 (좌우 영역 → 필드) | 외부 세계가 전장에 개입 | 지원형 슈퍼웨폰 (포격 지원, 폭격 편대 통과), 보스 등장 예고, 아군 편대 통과 |
| 확산 (필드 → 좌우 영역) | 필드의 사건이 화면 프레임을 넘어 세계에 영향 | 기체형 슈퍼웨폰 (대출력 레이저의 압력으로 좌우 영역의 구름이 밀려나는 연출), 대형 폭발의 충격파 확산 |

슈퍼웨폰의 연출 방향 분류(지원형/기체형)는 시스템_슈퍼웨폰 문서에서 정의한다.

설계 제약:
- 좌우 영역의 배경과 연출은 **시각 표현 전용**이다. 판정(피격/충돌)은 플레이필드 내부에서만 발생한다는 원칙을 유지한다
- 좌우 영역의 배경 요소는 필드의 게임플레이 오브젝트와 혼동되지 않아야 한다 (적처럼 보이는 배경물 금지 — 경계 처리와 명도 차이가 이를 보조)
- **HUD는 플레이필드 내 오버레이로 배치한다 (UI 기획 결정).** 좌우 영역에는 UI를 배치하지 않는다 — 시야 분산 방지 + 연출 예약 공간을 정보가 가리는 것 방지. 상세는 UI기획_인게임HUD 문서 참고

### 4.3 해상도 대응

- 기준 해상도와 지원 해상도 범위는 프로토타입 이후 결정
- 원칙: 플레이필드의 세로 시야(월드 기준 보이는 범위)는 모든 해상도에서 동일하게 유지한다. 해상도가 달라도 게임플레이 유불리가 생기지 않아야 한다

## 5. 월드 단위 규격

### 5.1 결정 방식

월드 단위의 구체 기준값은 **엔진에서 프로토타입 초기에 확정**한다. 본 문서는 기준 체계와 파생 관계만 정의한다.

### 5.2 기준 앵커와 파생 관계

**기준 앵커: 플레이필드의 세로 높이 (월드 단위)**

이 값 하나를 기준으로 다음이 비율로 파생된다.

| 파생 항목 | 관계 |
|-----------|------|
| 기체/잡몹/엘리트/보스의 기준 크기 | 플레이필드 세로 대비 비율로 정의 |
| 플레이어 이동 속도 | 플레이필드 세로를 몇 초에 종단하는가로 체감 정의 |
| 스크롤 속도 | 배경이 플레이필드 세로를 통과하는 시간으로 체감 정의 |
| 탄속 | 플레이필드 종단 시간으로 체감 정의 |
| 스테이지 길이 | 플레이 시간 × 스크롤 속도로 환산 |

이 방식의 의도: 엔진 기준값이 무엇이 되든, 모든 수치가 "화면 대비 체감"으로 정의되어 있으면 기준값 변경 시 일괄 환산이 가능하다. 프로토타입 사양서의 [제안] 수치들도 확정된 기준 앵커에 맞춰 환산하여 적용한다.

### 5.3 데이터 저작 좌표 규칙

저작 데이터의 좌표 공간은 세 가지로 분리한다. 하나의 규칙에 섞지 않는다.

| 좌표 종류 | 사용 대상 | 저작 기준 |
|-----------|-----------|-----------|
| 플레이필드 전역 좌표 | 스폰 위치, 이동 패턴 웨이포인트, 스크립트 이동 목표, 고정 범위 중심 | 플레이필드 정규화 좌표 |
| 소유자 로컬 좌표 | 발사구 오프셋, 보스 파츠 위치, 콜리전 오프셋 등 소유 객체에 종속된 위치 | 해당 프리팹의 로컬 앵커/로컬 좌표 (기동 문서의 공통 앵커 구조와 일치 — 전역 좌표로 재저작하지 않는다) |
| 거리·크기 | 사거리, 범위 반경, 이동속도, 탄속 | 플레이필드 세로 높이 대비 비율 |

**플레이필드 정규화 좌표:**

- X: -1.0 ~ +1.0 (0 = 가로 중앙, ±1 = 좌우 경계) / Y: 0.0 ~ 1.0 (0 = 하단, 1 = 상단)
- (0, 0) = 플레이필드 하단 중앙의 **경계점** — 플레이어 시작 앵커는 이 원점이 아니라 클램프 바운드를 반영한 최저 합법 위치다 (기동 문서 5.4)
- **화면 밖 진입·이탈을 위해 범위 초과값을 허용한다**: Y < 0 = 하단 화면 밖, Y > 1 = 상단 화면 밖, |X| > 1 = 좌우 화면 밖. 초과값도 동일한 정규화 스케일을 사용한다 (스폰 대기·진입 연출·재진입 경로 저작에 필요)

**월드 변환식 (기획 데이터와 구현의 공통 기준):**

- 월드 X = 플레이필드 중심 X + 정규화 X × (플레이필드 가로폭 ÷ 2)
- 월드 Y = 플레이필드 하단 Y + 정규화 Y × 플레이필드 세로 높이
- 역변환: 정규화 X = (월드 X − 중심 X) ÷ (가로폭 ÷ 2) / 정규화 Y = (월드 Y − 하단 Y) ÷ 세로 높이
- 범위 초과 좌표도 동일한 식으로 변환한다

**정규화 좌표는 위치 저작·저장 전용이다 (구현 계약):**

- 정규화 공간은 X와 Y의 스케일이 다르므로 (X 1.0과 Y 1.0이 같은 월드 거리가 아님), **정규화 좌표에서 직접 거리·방향 각도·이동속도·범위 반경을 계산하지 않는다** — 플레이필드 비율에 따라 결과가 왜곡된다
- 두 위치 간 거리·방향·보간·속도 계산은 반드시 **게임플레이 판정 평면의 월드 좌표로 변환한 뒤** 수행한다

**수치 단위의 역할 분리 (단일화):**

- 기획·마스터 데이터 저작값 = **플레이필드 세로 높이 대비 비율** (테이블마다 비율/월드 단위가 섞이지 않게 단일화)
- 수치의 차원 단위표 (H = 플레이필드 세로 높이):

| 수치 종류 | 저작 단위 |
|-----------|-----------|
| 거리·크기·반경 | H의 배수 (예: 폭발 반경 0.08 = 세로 높이의 8%) |
| 이동속도·탄속·스크롤 속도 | H/초 (예: 탄속 1.5 = 초당 세로 높이의 1.5배 이동) |
| 가속도 | H/초² |
| 시간·쿨다운 | 초 |
| 각도 / 회전속도 | 도 / 도·초 |
- 런타임 = 로드 시 현재 플레이필드 월드 크기 기준으로 월드 단위 환산
- 엔진 에셋 내부 로컬 트랜스폼 = 엔진 로컬 단위 사용 가능

월드 좌표 직접 입력은 사용하지 않는다 — 플레이필드 규격이 변해도 데이터가 깨지지 않게 하기 위함.

**프로그래머 테이블 설계 전달 사항:** 본 규칙 확정에 따라 스폰 위치 / 이동 패턴 웨이포인트·속도 / 탄환 속도·수명·범위 / 무기 사거리 / 범위 공격 반경 / 플레이어 이동속도 테이블은 위 좌표·단위 체계로 저작하고, 보스 파츠·발사구는 프리팹 로컬 앵커를 유지한다.

## 6. UI 영역

HUD 배치 원칙 (확정 — UI 기획 2호 결정 반영):

- HUD는 **플레이필드 내부 오버레이**로 배치한다
- 좌우 월드·연출 영역에는 UI를 배치하지 않는다 (시선 분산·연출 충돌 방지)

세부 레이아웃·표시 정보는 UI기획_인게임HUD 문서에서 정의한다.
